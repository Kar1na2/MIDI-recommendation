# AMT migration audit

Audit date: **November 4, 2026 (America/Los_Angeles)**. Scope: the current working tree, including ignored local outputs, untracked experiments, installed backend source, and generated exports. This is a first-phase audit, not a transcription implementation or a model-selection decision.

## 1. Findings and scope

**Spotify Basic Pitch is the legacy harmonic/bass transcriber. It is not the analysis engine used by `rhythm-harmony-v1` or by the Silo “meaningful love” Other-stem diagnostic.** That diagnostic computes acoustic features directly from WAV files. Its failures cannot be fixed merely by replacing Basic Pitch imports.

There are several parallel systems, rather than one audio → MIDI → rhythm pipeline:

1. The legacy corpus pipeline: Demucs → Basic Pitch for Other/Bass and ADTLib for Drums → merged MIDI → chord-guided note review/correction → note sequences, alignments, reports, and web exports.
2. Independent chord analysis: Other WAV → Chordino/Vamp → chord segments/sequences and chord comparisons. Note tagging joins these results to legacy MIDI, but chord extraction itself does not consume that MIDI.
3. Instrumental catalog analysis (`instrumental-stem-patterns-v4`): dedicated instrumental recording → Demucs → one-second acoustic summaries → arrangement/texture windows. No MIDI input.
4. The local rhythm/vocal preview (`rhythm-harmony-v1`): instrumental stem WAVs → spectral-flux attacks/chroma → beat grid, recurrence and boundaries, with a separate vocal-text alignment branch. No Basic Pitch event input.
5. Already-present, untracked experimental transcription: ByteDance piano/pedal, pYIN bass, ADTOF drums, and a pinned YourMT3+ model under `scripts/amt/`. These are not wired into the rhythm preview or legacy production readers.

**Historical predicted events are untrusted hypotheses.** This applies to Basic Pitch MIDI, corrected descendants, cached sequence JSON/CSV, specialist outputs, and YourMT3+ experiments. None becomes ground truth by having been saved, corrected automatically, or generated by a newer model.

### Installed initialization and backend selection

The inspected installed package is `.venv/lib/python3.11/site-packages/basic_pitch/`:

- `__init__.py:73–94` selects the ICASSP 2022 artifact format based on available TensorFlow/CoreML/TFLite/ONNX runtimes. These are **execution formats of Basic Pitch**, not independent replacement AMT systems.
- `inference.py:70–146` implements `Model`; the TensorFlow path calls `tf.saved_model.load` at line 83. `run_inference` at lines 281–284 reuses a supplied `Model` instance **or creates one from a supplied path**.
- The repository passes a model **path** on each prediction. Therefore, the harmonic script's “build the model once” comment at lines 117–120 is misleading: importing once is not retaining one initialized `Model`. Installed source constructs the model again for each path-based call.
- `inference.py:414–425` defaults to `minimum_note_length=127.70` ms and `midi_tempo=120`. The current stem wrapper inherits these; archived whole-file conversion overrides minimum duration to 58 ms. The 120-BPM MIDI metadata is not an estimated musical tempo.
- `inference.py:229`; `constants.py:22–32`: audio is loaded mono at **22,050 Hz**, with a 256-sample analysis hop and an 88-semitone note range starting at 27.5 Hz. Model onset/frame/contour activations then pass through Basic Pitch's note-formation logic.
- Installed `.venv/lib/python3.11/site-packages/basic_pitch-0.4.0.dist-info/entry_points.txt:1–3` exposes `basic-pitch = basic_pitch.predict:main`; historical CLI runs can save MIDI, event CSV and raw NPZ independently of the repository wrapper.

## 6. Source separation and audio preprocessing

### Original-corpus backend

`scripts/separation/separate_stems.py:28–33,44–63,77–107` uses **Demucs `htdemucs_ft`**, selects CUDA if available, supports CPU, and invokes the CLI in batches. It reads `.mp3` files in three source directories. Jobs and completeness are keyed by recording basename, not content identity. All four output files constitute completion. Default Demucs output settings are inherited rather than fully pinned in a per-run manifest.

The separator can remove/replace a pre-existing song stem directory while finalizing a rerun (`separate_stems.py:103–105`). This audit did not run it. Future migration work must not use a corpus rerun as a harmless cache-refresh operation.

### Dedicated instrumental backends

- `scripts/instrumentals/separate.py:32,67`: subprocess backend, validates four Demucs outputs and finalizes only Bass/Drums/Other compact previews. Uses ffmpeg mono 22.05-kHz PCM-16 conversion; vocal residual is discarded from this catalog's published stems.
- `scripts/instrumentals/separate_api.py:28–58,86–111`: persistent `demucs.api.Separator(model='htdemucs_ft', shifts=1, overlap=0.25)`. Averages channels to mono, jointly peak-scales all three desired stems, resamples to 22.05 kHz with `resample_poly`, writes PCM-16, and checks duration/format. Omits only bag components with no contribution to desired stems; preserves their weights.
- `separate_api.py:61–74` can reuse another track's stems for identical source audio SHA-256. Reuse checks file existence/duration, **not model/config identity**.
- SQLite statuses drive separation/analysis queues. `analyze.py:266` normally selects `separated`, optionally failed/ready rows; changing the method version does not itself invalidate ready tracks.

### Other preprocessing

- Chordino receives mono-averaged WAV at its source sample rate (`extract_chords.py:77–87`).
- Rhythm v1 resamples mono to **11,025 Hz**, peak-normalizes, uses FFT 2,048/hop 256 (about **186-ms windows / 23.2-ms steps**), 24 mel bands, chroma and normalized spectral shape (`patterns.py:22,30–68`). This is acoustic feature preprocessing, not AMT.
- Catalog v4 uses mono **22,050 Hz**, FFT 2,048/hop 512; aggregates MFCC/chroma/RMS/centroid/onset strength per second and robustly standardizes/clips them (`scripts/instrumentals/analyze.py:33–61`).
- Specialist transcription crops explicit windows, averages channels, resamples to **16 kHz**, and shifts results back to source time (`transcribe_specialist.py:73–88,122`).
- YourMT3 transcription uses SoundFile window reads, finite-value validation, mono averaging and model-config sample rate; source start is derived from sample index, and exported notes retain absolute source seconds (`amt/transcribe.py:80–90,116–154`).

## 7. Rhythm-analysis algorithms, limitations and the Meaningful Love finding

### Rhythm-harmony-v1

`scripts/rhythm_layers/patterns.py` implements:

1. Positive changes in log-mel energy averaged across 24 bands; `librosa.onset.onset_detect(normalize=True, delta=.09, wait=2)` produces sparse attack times (`extract:41–69`).
2. Equal-mean Bass/Drums/Other flux envelope and `beat_track(start_bpm=110, tightness=75)`; fallback is a **120-BPM grid with zero confidence** if evidence is insufficient (`pulse:72–93`). This is not meter/downbeat estimation.
3. Four subdivisions per estimated beat. Attacks map to the nearest slot within 0.18 seconds, becoming **binary occupancy**; simultaneous attacks and multiple events in a slot collapse (`grid:96–111`). Chroma combines octave registers.
4. Tolerant attack distance uses neighboring slots at weight .35 and `np.roll` (`event_distance:114–119`); its wraparound also connects opposite ends of finite windows. Phase boundaries therefore need testing.
5. Broad/fine boundaries compare eight/four-beat contexts, respectively, every beat. Rhythm/harmony/shape weights are **.72/.23/.05** and **.58/.27/.15**. Threshold is `max(.24 or .20, median + 1.4*MAD)`, prominence .07, minimum spacing eight/six beats, strongest automatic changes capped at four/six (`changes:144–177`). Fine rings inherit broad boundaries.
6. Repeat search tests only **1, 2, 4, 8, 16 beats**, requires two lag lengths of available material, combines .75 rhythm + .25 harmony, prefers the shortest candidate within .025 of best, then requires weighted score ≥.60 **and** rhythm ≥.55 (`cycle_summary:180–241`). The pre-gate shortest-choice rule can reject a selected candidate without reconsidering another candidate that passes.
7. Rising/falling “contour” uses dominant **pitch class** only at accepted attacks and wrapped intervals, not full note pitches, voice separation or pitch register (`cycle_summary:227–238`). Tidal notation marks part-name attacks/rests, not a transcribed score.
8. Listening overrides can remove automatic cuts, insert supplied anchors and replace labels (`make_layers:244–285`; `build_preview.py:125,135–150`). These are annotations, not model discoveries.

Overlapping/polyphonic pitched notes, soft attacks, sustained pads, independent layers, expressive timing, non-power-of-two phrases, octave movement and reattacks can all fail this representation **without Basic Pitch being present**. DTW exists in `timeline_map` for matching recording clocks; it is **not** used to search local recurring phrases in `cycle_summary`.

## 10. Migration risks

1. **Fixing the wrong branch.** Replacing Basic Pitch cannot repair the WAV-based rhythm representation. The preview must explicitly switch to new note-event inputs, with independent validation of beat/phrase algorithms.
2. **Stale corrected files and exports overriding new events.** Fixed directories, presence/mtime checks and global fallback order can mix old/new predictions without any Basic Pitch import.
3. **Model-specific postprocessing.** Chord-tone correction can change valid nonchord tones; octave deduplication can remove valid voices. New model outputs must not inherit these edits silently.
4. **Instrument/clock information loss.** Legacy merge collapses tracks by stem; “Other” is not an instrument. Original/dedicated versions, crops, padded model segments, pedal key-off and audible decay need explicit handling.
5. **Unvalidated newer-model outputs.** Existing fp32 Silo Other run has 53 notes and decoding errors (one missing onset, five tie merges); float16 v2 has 61 notes. Mix run has 147 notes and eight onset/eight tie errors. Early run lacks metadata; older manifests omit precision. Research notes flag implausibly short piano durations and no verified pitch-plus-duration repeats. These are not demonstrated accuracy improvements.
6. **Implicit model/weight behavior.** Basic Pitch runtime-format fallback is still Basic Pitch; archived missing-backup inference can restore it; ADTOF can execute without loaded pretrained weights; piano package may download a missing/undersized checkpoint internally. New adapters must fail closed on unavailable/unverified weights and must never install/download during ordinary analysis implicitly.
7. **Supply-chain identity and unsafe serialization.** The Basic Pitch inspector uses pickle-capable NPZ loading. Downloaded YourMT3 upstream dataset code uses object `.npy`/pickle loading (`utils/datasets_train.py:412,442`, `datasets_eval.py:131,137`) and model loading uses `torch.load(weights_only=False)`. These upstream dataset paths are not current inference inputs, but must not become arbitrary historical-cache loaders. Verify trusted files before loading; prefer a non-object canonical event format.
8. **Environment drift.** CUDA Torch, CPU TensorFlow, legacy ADTLib and Windows/WSL specialists differ. Main uv resolution does not lock every optional dependency or shared-environment package.
9. **Evaluation leakage and annotation bias.** User listening anchors, model-derived review samples, corrected estimates, score MIDI and synthetic fixtures are distinct evidence classes. None establishes full-recording pitched-note accuracy without reviewed aligned labels.
10. **False confidence from representation limits.** Exact quantization, pitch-class folding, assumed bars, shortest-lag selection and sparse event loss can create misses or spurious repeats even with accurate transcription. Rhythm-only equality does not establish pitch or phrase identity.

## 11. Proposed clean AMT-first architecture

Select a backend after benchmark evidence. Build the boundary around model-independent, explicit musical-event artifacts; do not define the new system as a renamed `predict()` wrapper.

```text
immutable recording registry (original bytes, SHA-256, source/version identity)
  → deterministic decode / model-specific audio preparation
  ├─ direct-mix AMT adapter ──────────────────────┐
  └─ versioned optional source separation        │
       → per-stem / specialist AMT adapters ─────┤
                                                ↓
  immutable raw predictions + canonical note-event table + run manifest
    → validation / explicit reviewed edits (new derivative, never overwrite)
    ├─ note/voice/attack-group representations and recurring phrase search
    ├─ rhythm-only, full-pitch, interval/transposition, duration representations
    └─ independent beat/downbeat hypotheses and seconds↔beat mappings
         → layered motifs, persistent figures/overlays and section candidates
         → retrieval / comparison / reports / explicitly versioned UI export

independent audio chord estimates / lyric alignment / acoustic diagnostics
  → separately identified evidence joined by recording ID + verified clock
```

### Required contracts

- **Input identity:** recording ID and original hash, selected mix/stem hash, separation run/model/checkpoint/config, sample-rate/channel/resampling policy, source interval and exact clock transform. A Spotify ID/title alone is insufficient.
- **Run identity:** immutable run ID, code revision plus dirty-tree identity, dependency lock, backend implementation revision, checkpoint hash, precision/device/seed/batch/decoding parameters, schema version, status/errors, timings and output hashes. Cache identity hashes all semantic inputs/configuration; never use existence alone.
- **Canonical events:** stable event/track IDs, onset/offset in absolute input seconds, full MIDI pitch, predicted instrument/program and drum flag, velocity if available, confidence if actually supplied (otherwise null), source run, raw-event link, and review/edit history. Retain simultaneous voices, same-pitch reattacks, pedal/controller information and carry-in notes separately from attacks. MIDI is an export/interchange artifact, not the sole provenance store.
- **Explicit uncertainty:** model labels are predictions; key-off duration differs from pedal/sounding duration. Beat/meter/chord labels are separate estimates. Quantization produces derived representations while preserving raw timing and register.
- **No fallback contamination:** a failed selected backend yields an explicit failed/pending result. Never recover by reading `midi/`, `merged/`, `corrected/` or a prior model result. Legacy comparison is a named, read-only baseline mode.
- **Separate human evidence:** listening/phrase annotations are versioned review inputs; automatic runs omit them unless explicitly requested. Model-generated or auto-corrected notes are prohibited as ground truth/training labels.
- **Safe downstream selection:** every analyzer/exporter receives explicit recording/event/beat/chord run IDs; reject mixed or missing ancestry. Build candidate retrieval and comparison results from the same event snapshot.
- **Operational bounds:** stream/batch long recordings with validated overlap/tie/reattack handling; measure peak memory, latency and CPU fallback on this workstation before corpus execution. Verify complete weight loading and prohibit silent downloads.

The existing `scripts/amt/` prototype provides useful grouping/evaluation/manifest ideas. It is a candidate foundation to review, not an already accepted production migration. Improve checkpoint/source verification, complete dependency isolation, decoding, long-audio memory behavior and approximate phrase matching before connecting it to the player.

## 13. Recommended implementation order

1. **Review this audit and snapshot provenance.** Preserve all sources/historical runs; record artifact hashes and known/unknown lineage. Keep Silo and 1nonly evaluation identities distinct.
2. **Create the new run/artifact boundary first.** Implement explicit input/output schemas, immutable run IDs, semantic cache keys and legacy-read exclusion. Add sentinel contamination tests before introducing a replacement transcriber.
3. **Build reviewed benchmark windows.** Complete aligned pitched-note references, onset/offset semantics and source-clock checks. Do not use historical Basic Pitch/specialist/YourMT3 predictions as answers.
4. **Audit and select candidate adapters.** Review existing YourMT3+/specialist source and weights; verify any service's implementation to the extent possible and record unknowns. Pin versions and plan installation separately; no automatic model install in this phase.
5. **Implement one adapter behind the boundary.** Fail on missing/unverified weights; preserve raw predictions/errors and clocks, support long-audio chunking, produce canonical events and MIDI. Validate on the frozen windows before a corpus run.
6. **Replace the pitched representation in rhythm analysis.** Consume explicit note events, preserve register/polyphony/reattacks, separate durations from attack timing and add phrase recurrence beyond fixed beat lags. Evaluate beats, sections and overlays independently of AMT quality.
7. **Migrate downstream consumers explicitly.** Replace global directory discovery and corrected-file fallback, retain multi-instrument identities, revalidate correction heuristics, and regenerate joins/sequences/retrieval/statistics/database tables under the selected new run.
8. **Build a versioned preview/export.** Show raw predictions, uncertainty, reviewed edits and clock/source provenance; keep historical views separately named. Verify no old JSON/manifest/browser data is presented as new AMT evidence.
9. **Run a bounded comparison, then expand.** Compare models on identical inputs/references with recorded runtime/memory; investigate decoding/duration errors before full-library processing. Continue only when measured quality and operational bounds meet the stated acceptance criteria.
10. **Retire Basic Pitch from normal operation after parity is established.** Remove its production dependency/dispatch paths and update lockfiles/docs/config; keep an explicitly optional, isolated historical baseline if needed. Do not delete historical event evidence or source audio as part of dependency removal.
